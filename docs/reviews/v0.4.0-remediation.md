## Remediated findings

### COV-5 — Overlapping-entry / contiguous-range ZIP defense untested

- **Review ID:** COV-5
- **Original severity:** Low (coverage gap)
- **Validation method:** New hostile test `overlappingEntryArchiveIsRejected (zip-overlap attack)` in `src/update/archive.test.ts`, exercising the real (non-mocked) `extractVerifiedArchive` against a crafted overlapping-entry archive.
- **Evidence:** The test crafts an archive where entry A's data region contains entry B's complete local-file-header + payload. Entry B's central-directory record points `relativeOffsetOfLocalHeader` into A's data range (via the new `localOffset` option) and omits B's local header from the concatenated local bytes (via the new `includeLocal: false` option). `extractVerifiedArchive` must reject this with `GOAT_UPDATE_ARCHIVE_INVALID` because the contiguous-range walk in `preflightArchive` requires each entry's `[localStart, dataEnd)` to abut the previous one with no overlap and no gap. The test also asserts the staging root is left empty.
- **Disposition:** **Fixed.**
- **Root cause:** The test fixture builder (`zip-fixture.ts`) had no way to override the central-directory local-header offset or omit an entry's local bytes, so no overlapping-entry case could be constructed.
- **Files changed:**
  - `test/v0.4.0-update/zip-fixture.ts` — added `localOffset` and `includeLocal` options to `TestZipEntry`; added exported `buildEntryLocalBytes` and `computeCrc32` helpers.
  - `src/update/archive.test.ts` — added `overlappingEntryArchiveIsRejected (zip-overlap attack)` test; imported `buildEntryLocalBytes`.
- **Fix:** Test infrastructure extended to support overlapping-entry archives; new hostile test proves the contiguous-range walk rejects the classic zip-overlap attack.
- **Regression tests:** `overlappingEntryArchiveIsRejected (zip-overlap attack)` in `src/update/archive.test.ts`.
- **Remaining limitations:** None for this finding.

### D-7 — Legacy v1 manifest parser accepts duplicate object keys

- **Review ID:** D-7
- **Original severity:** Defense-in-depth (not a vulnerability; signature verification remains authoritative)
- **Validation method:** New regression tests `parseManifest rejects duplicate JSON object keys` and `parseManifest accepts a valid manifest without duplicate keys` in `src/engine/validate.test.ts`; the scanner is exercised against a manifest with a duplicate `engineVersion` key.
- **Evidence:** `assertNoDuplicateObjectKeys` scans the raw JSON text before `JSON.parse` and rejects any duplicate object key at the same nesting scope. The scanner handles escaped characters and multi-line strings correctly (it delegates string decoding to `JSON.parse` on the extracted token). A duplicate `engineVersion` key now throws `GOAT_ENGINE_MANIFEST_INVALID` before the manifest is parsed. The valid-manifest test confirms no false positives.
- **Disposition:** **Fixed (defense-in-depth hardening).**
- **Root cause:** The legacy `parseManifest` used `JSON.parse`, which silently resolves duplicate JSON object keys last-wins. The v0.4 `parseCanonicalJson` rejects duplicate keys outright; the legacy path now matches that invariant.
- **Files changed:**
  - `src/engine/validate.ts` — added `assertNoDuplicateObjectKeys` and `readJsonStringToken` helper; `parseManifest` now calls the scanner before `JSON.parse`.
  - `src/engine/validate.test.ts` — imported `parseManifest`; added two regression tests.
- **Fix:** The legacy parser now rejects duplicate keys before signature verification, matching the v0.4 canonical-JSON invariant. Signature verification is unchanged and remains the authoritative trust gate.
- **Regression tests:** `parseManifest rejects duplicate JSON object keys`, `parseManifest accepts a valid manifest without duplicate keys` in `src/engine/validate.test.ts`.
- **Remaining limitations:** None. The scanner is additive; it cannot weaken signature verification.

### COV-4 — Native health test silently skips when no C compiler is present

- **Review ID:** COV-4
- **Original severity:** Low (coverage gap)
- **Validation method:** CI workflow inspection — the `Verify C compiler` step now explicitly checks `Get-Command` and exits with a clear error message if the compiler is absent.
- **Evidence:** `.github/workflows/test.yml` `Verify C compiler` step now runs `if (-not (Get-Command $cmd -ErrorAction SilentlyContinue)) { Write-Error ...; exit 1 }` before `& $cmd --version`. If the MinGW install step fails on `windows-latest` or `cc` is missing on `macos-latest`, the CI job fails loudly instead of letting the native health test skip silently.
- **Disposition:** **Fixed.**
- **Root cause:** The original step ran `& $cmd --version` without gating on the compiler's existence; a missing compiler would cause the native health test to `context.skip` with no CI failure signal.
- **Files changed:**
  - `.github/workflows/test.yml` — `Verify C compiler` step now explicitly fails when the compiler is not on PATH.
- **Fix:** CI fails the job when the C compiler is absent, ensuring the native health test does not silently skip.
- **Regression tests:** CI workflow run on `windows-latest` + `macos-latest` (the step itself is the gate).
- **Remaining limitations:** None for this finding.

## Findings NOT remediated (with reasons)

### COV-1 — Real platform code-signing verification never exercised (High)

- **Review ID:** COV-1
- **Original severity:** High (coverage gap; release-gating)
- **Disposition:** **Not fixed — environmental limitation.**
- **Root cause / why not fixed:** This requires compiling `fixture-engine.c` with a C compiler (MinGW on Windows) and running the real `powershell.exe` with `Get-AuthenticodeSignature` against the signed and unsigned binary. **No C compiler is available in this environment** (the native health test skips for the same reason — see the review's §8). Additionally, producing a valid Authenticode-signed fixture requires a test signing certificate that is not present. GLM 5.2 assessed this as outside its comfortable capability on Windows without a compiler and test certificate.
- **Required remediation (for a future pass with GPT-5.6 Sol or Kimi K3 on a CI runner):** A native code-signing test gated on tool availability (`context.skip` when absent, like `health.native.test.ts`) that compiles the fixture, runs `verifyPlatformCodeSignature` with the default runner against the unsigned binary (assert `GOAT_UPDATE_CODE_SIGNATURE_INVALID`), and on platforms with a test signing identity, signs the fixture and asserts acceptance/rejection per identity match.
- **Remaining limitations:** The code-signing verification path remains mocked in all tests. Production updates are fail-closed in v0.4.0, so this gates enabling production trust, not shipping the launcher.

### COV-2 — Locked Windows executable activation untested (Medium)

- **Review ID:** COV-2
- **Original severity:** Medium (coverage gap)
- **Disposition:** **Not fixed — environmental limitation.**
- **Root cause / why not fixed:** This requires a Windows-native test that spawns and holds the active engine executable open (e.g., via a child process that keeps a file handle), runs a full `runVerifiedUpdate`, and asserts the deferred-cleanup path triggers while the activation chain remains consistent. While GLM 5.2 could write the test scaffolding, the test depends on real Windows file-locking behavior (a running executable cannot be deleted) and on the full `runVerifiedUpdate` flow with a mocked TUF server. The review restrictions forbid "replacing meaningful filesystem or native tests with mocks," and the locked-exe behavior is precisely the native behavior that must not be mocked. Without a C compiler to build a real fixture engine that can be held open, and without confidence that a `Buffer.from("fake-engine")` file reproduces the Windows lock semantics, GLM 5.2 assessed this as risky to implement incorrectly and left it for a pass with compiler access.
- **Required remediation:** A Windows-native test that spawns/holds a compiled fixture engine executable open, runs `runVerifiedUpdate` to a new release, and asserts activation succeeds, the old slot is removed or reported in `deferredCleanupPaths`, and `loadActivationChain` + `validateInstalledActivation` remain consistent.
- **Remaining limitations:** The locked-exe deferred-cleanup design is sound by code reading but unproven by a hostile test. Not exploitable in v0.4.0 (fail-closed).

### COV-3 — macOS `codesign`/`spctl` real-output parsing unverified (Medium)

- **Review ID:** COV-3
- **Original severity:** Medium (coverage gap; cross-platform)
- **Disposition:** **Not fixed — wrong platform.**
- **Root cause / why not fixed:** This requires running real `codesign --display --verbose=4` and `spctl --assess --type execute` on macOS against a Developer-ID-signed fixture. **This environment is Windows (`win32`)** — the macOS tools do not exist here. GLM 5.2 cannot execute or validate macOS-native behavior from Windows.
- **Required remediation (for a pass on macOS):** A native macOS test (skip if `codesign`/`spctl` absent) verifying rejection of an unsigned/ad-hoc-signed fixture and acceptance logic against a Developer-ID-signed fixture where available in CI.
- **Remaining limitations:** The `TeamIdentifier=`/`Authority=` line parsing and `authorities[0]` ordering assumption are validated only via mocks. Not exploitable in v0.4.0 (fail-closed).
