# GOAT v0.4.0 — Independent Hostile Security Review

- **Reviewer:** Independent (not the implementer)
- **Scope:** `goatcli` package, installed command `goat`, version `v0.4.0 — Packaging and verified updates`
- **Branch:** `feat/v0.4.0-packaging-updates` (working tree, uncommitted) at `goatcli/`
- **Primary security boundary:** downloading and activating executable engine code
- **Platforms in scope:** Windows and macOS
- **Review date:** 2026-07-27
- **Environment used for hostile experiments:** Windows (`win32`), Node 24.18.0, PowerShell 5.1.26100.8875, Windows build 10.0.26200.0. Every PROBE/EXP block below was executed with these exact versions; reproducibility requires the same.

## 1. Methodology and evidence base

I reviewed the **complete current change set** for v0.4.0, not the implementer's summary.

**Change set identified.** `main` is a near-empty initial commit; the entire application lives on unmerged feature branches. The v0.4.0 work is the **uncommitted working-tree state** on `feat/v0.4.0-packaging-updates`:

- 12 committed files modified in the working tree: `.github/workflows/test.yml`, `package.json`, `scripts/check-privacy-architecture.mjs`, `scripts/verify-package.mjs`, `src/cli.ts`, `src/cli.test.ts`, `src/engine/contract.ts`, `src/engine/launch.ts`, `src/privacy/release-policy.ts` (+ two `.generated.ts`), `src/version.ts` (and `package-lock.json`).
- The **entire `src/update/` subsystem is new/untracked** (~30 production modules + tests), plus new `src/commands/update.ts`, `src/commands/version.ts`, and `test/v0.4.0-update/` (mock server, TUF fixture, update-bundle fixture, crash worker, ZIP fixture, native C fixture + test-only cert/key).

**Read in full:** both required design docs (`docs/security/v0.4.0-update-trust-design.md`, `docs/security/v0.4.0-update-acceptance-matrix.md`); every production module in `src/update/` (download, network, selection, policy, temporary, archive, trust, schema, canonical-json, metadata, metadata-client, receipt, activation, activation-record, recovery, rollback, state, journal, lock, durable, code-signing, health, compatibility, installed, updater, errors, trusted-root.generated); the changed `src/cli.ts`, `src/commands/update.ts`, `src/commands/version.ts`, `src/version.ts`, `src/engine/launch.ts`, `src/privacy/release-policy.ts`; `.github/workflows/test.yml`; `scripts/verify-package.mjs`; `scripts/check-privacy-architecture.mjs`; and all `test/v0.4.0-update/*` fixtures.

**Tests run.** `npm test` (build + `node --test`): **300 passed, 0 failed, 1 skipped.** The single skip is `native fixture engine passes the launcher health check` (`src/update/health.native.test.ts`) with reason `no C compiler available for native fixture engine` — no C compiler is present in this Windows environment. (CI installs MinGW on `windows-latest`; see §6.)

**Hostile experiments performed (all temporary; artifacts removed before finishing).** Each exercised the **real compiled production modules** via `tsx`, not mocks:

*Pass 1 (initial):*

1. **Windows junction at `stagingRoot/bin`** placed before `extractVerifiedArchive`. Result: `THREW GOAT_UPDATE_TEMPORARY_FILE_UNSAFE`; outside sentinel file left intact.
2. **Duplicate JSON object keys** fed to `parseCanonicalJson`. Result: `GOAT_UPDATE_MANIFEST_INVALID`.
3. **Case-colliding archive entry names** (`LICENSE` + `license`). Result: rejected (`GOAT_UPDATE_ARCHIVE_LIMIT`). Note: this particular experiment was rejected by the **entry-count guard** (`eocd.entryCount !== target.custom.contents.length`, because the extra `license` entry makes 8 vs. 7 signed) — *not* by the duplicate-normalized-path guard. The duplicate-normalized-path / case-collision defense itself is confirmed via `archive.test.ts:duplicateNormalizedPathsAreRejected` (test reading), not by this hostile experiment. The experiment nonetheless confirms that an attacker cannot smuggle an extra colliding entry past preflight.
4. **Trailing suffix after EOCD.** Result: `GOAT_UPDATE_ARCHIVE_INVALID`.
5. **`lstat` junction probe:** Node `lstat` reports a Windows junction as `isSymbolicLink() === true`; `assertNoLinkOrReparsePath` catches it (`GOAT_UPDATE_TEMPORARY_FILE_UNSAFE`); `realpath` resolves the junction to the outside target (≠ junction path), so the `realpath === path` check in `durable.ts` also fires.
6. **Real (non-mocked) code-signing + health probe:** attempted to compile `fixture-engine.c` and run `verifyPlatformCodeSignature` (Windows Authenticode via the default PowerShell runner) and `runEngineHealthCheck` (default `spawnSync` runner). **No C compiler available locally** → probe could not execute (mirrors the skipped test; CI has MinGW).

*Pass 2 (deeper, after feedback that the first review was not deep enough):*

7. **TUF trust-store attack suite (6 cases against the real `TufTrustStore`/`metadata.ts`):**
   - channel metadata signed by only 1 of 3 keys (needs threshold 2) → `GOAT_UPDATE_MANIFEST_INVALID` ✅
   - duplicate identical signatures from one key → `GOAT_UPDATE_MANIFEST_INVALID` (`validateSignatures` rejects duplicate keyids) ✅
   - a root-role keyid reused inside the targets role (cross-role key reuse) → `GOAT_UPDATE_MANIFEST_INVALID` (`validateRootSigned` enforces disjoint role key sets) ✅
   - timestamp `snapshot.json` version bumped to 999 while the real snapshot stays at 1 (mix-and-match) → `GOAT_UPDATE_METADATA_MISMATCH` ✅
   - timestamp signed by a targets-role key (wrong role) → `GOAT_UPDATE_SIGNING_KEY_UNKNOWN` ✅
   - root version below the trusted floor (replay of an old root) → `GOAT_UPDATE_METADATA_REPLAYED` ✅
   All six held. No threshold-bypass, cross-role, mix-and-match, or replay path was found.
8. **PowerShell `-Command` argument-injection probe (`code-signing.ts` exact invocation shape):** I confirmed from source that production invokes `spawnSync(powershell, ["-NoLogo","-NoProfile","-NonInteractive","-ExecutionPolicy","RemoteSigned","-Command", <script-string>], { shell: false, … })` where `<script-string>` is the literal `$signature=Get-AuthenticodeSignature -LiteralPath $args[0]` and the **executable path is passed as a separate trailing argv element** (becoming `$args[0]`), never interpolated into the `-Command` text. I reproduced this exact shape with a hostile `executablePath` containing `;`, `|`, `$(…)`, and backtick. In every case `PWNED` did **not** appear; PowerShell treated the path as a single `$args[0]` token and failed loading the security module rather than executing the injected text. **Precondition / defense-in-depth note:** non-injectability is *contingent on `shell:false` being preserved* — a future regression to `shell:true` would reintroduce interpretation of the argv as a shell command line. Additionally, `-File <script> -LiteralPath <path>` (passing the path as a named `-File`/parameter argument rather than via `-Command` + `$args[0]`) would be the stricter defense-in-depth choice; the current `-Command` form is safe only because of the `shell:false` + separate-argv combination. (`assertRegularExecutable` additionally requires the path to be an absolute, non-symlink, single-link regular file before the command ever runs, so an attacker-controlled path with shell metacharacters would already be rejected earlier.)
9. **Canonical-JSON parser edge suite (14 cases against `parseCanonicalJson`):** `1e0`, `-0`, `0.0`, an unsafe-large integer, a NUL byte in a key, a surrogate-pair key, surrounding whitespace, reordered keys, depth-65 nesting, `\t`/`\u0000` in strings, deep duplicate keys, leading-`+`, and hex ints **all threw `GOAT_UPDATE_MANIFEST_INVALID`**. Only a literal empty-string key `{"":1}` was accepted (harmless: canonical form identical). The parser does not rely on `JSON.parse` for object key handling, so duplicate-key ambiguity is rejected before any signature is interpreted.
10. **Windows held-file TOCTOU probe (download.ts guard):** on `win32`, `stats.ino` is **non-zero and stable** across `handle.stat()`/`fs.stat()` calls (so the `dev/ino/nlink` checks in `assertHeldArtifactUnchanged` are meaningful, not a no-op); `rename(replacement, heldPath)` **while the handle is open fails with `EPERM`**, and a subsequent read through the held handle returns the **original** bytes. The held-file-descriptor design therefore resists pathname-swap substitution on Windows. **Filesystem/sharing-mode assumption:** production opens the held file with `fs.open(path, "r+")` (no `FILE_SHARE_DELETE`), matching the probe's `O_RDWR`. The result is proven on **NTFS** (the supported Windows install target). It is **not** claimed for FAT32/exFAT (some USB/removable installs), where inode semantics differ and an open handle may not prevent rename/replace — GOAT does not install to removable FAT media in its supported configuration, but if that ever changes this guard must be re-proven. State this assumption when relying on the inode guard.
11. **Legacy v1 manifest duplicate-key probe (the path actually taken in the shipped build — see §2):** a manifest carrying a **duplicate `engineVersion` key** (`…"engineVersion":"0.4.0","engineVersion":"9.9.9"…`) is **accepted** by the legacy `parseManifest` (`validate.ts`, `JSON.parse` last-wins), yielding `engineVersion = "9.9.9"` — while the v0.4 `parseCanonicalJson` rejects the same bytes outright. This is a real parser divergence (see D-7 below), but it is **not exploitable**. The ed25519 signature in `validateManifestTrust` is verified over `canonicalEngineManifestPayload(manifest)`, which re-serializes the *parsed* object. Two cases exhaust the possibilities: **(a)** the duplicate changes the surviving value (e.g. a hostile `engineVersion` placed *after* the legitimate one, last-wins) → the re-serialized canonical bytes differ from what was signed → signature verification **fails, fail-closed**; **(b)** the duplicate does not change the surviving value (e.g. a hostile value placed *before* the legitimate one, which last-wins discards) → the re-serialized canonical bytes are identical to the signed form → signature verifies, but the accepted value is the **legitimate** one, so no hostile value is honored. There is no third case: an attacker without the signing key cannot produce a signature over a hostile canonical form, and `JSON.stringify` is deterministic for a given parsed object. The divergence is therefore a defense-in-depth weakness (the parser should reject duplicate keys outright, as `parseCanonicalJson` does), not a vulnerability.

*Pass 3 (deeper, after feedback that the second pass was still not deep enough — focused on the archive, download/network, selection, activation/rollback/recovery, journal hash-chain, CI workflow, and crypto-library axes that passes 1–2 only read but did not stress-test):*

12. **Real HTTP 3xx redirect (EXP12):** a live `http` server returning `302` with a `Location: http://attacker.example/...` header, fetched via the real `FixedOriginTransport`. Result: `GOAT_UPDATE_REDIRECT_REJECTED` (every 3xx is rejected in `validateResponse` before the body is read; `readResource` never follows redirects — there is no redirect-following code path at all). This complements the mocked `everyRedirectClassIsRejected` test (301/302/303/307/308) with a real socket.
13. **`http://` origin rejected at construction (EXP13):** `new FixedOriginTransport({ origin: "http://127.0.0.1:..." })` throws `GOAT_UPDATE_NETWORK_POLICY` at construction (`validateOrigin` requires `protocol === "https:"`, no userinfo, pathname `/`, no query/hash). There is no code path that ever constructs an `http:` transport — `compiledVerifiedUpdatePolicy` only ever feeds a policy whose origins are `null` (v0.4.0) or `https:` (future production). HTTPS-to-HTTP downgrade is therefore structurally impossible: the origin is fixed once at construction and `resolveResourceUrl` re-asserts `result.origin === origin.origin` per request.
14. **Archive contiguous-range / overlapping-entry defense (code-reading + attempted hostile probe):** `preflightArchive` (archive.ts) walks every entry sorted by `localStart` and asserts `range.localStart === expectedStart` with `expectedStart` advanced to each `range.dataEnd`, then asserts `expectedStart === eocd.centralDirectoryOffset`. This enforces that local-file-header regions are **contiguous, ordered, gap-free, and end exactly at the central directory** — the classic zip-overlap attack (one entry's local header embedded inside another's data, so two entries decode overlapping bytes to different contents) is rejected because the embedded "inner" local header occupies a byte range that the "outer" entry already claims, breaking the contiguity invariant. My hostile probe (an outer entry whose data bytes are crafted to be a valid inner local-file-header + payload, with the inner central-directory entry pointing into that range) could not be exercised end-to-end because `preflightArchive` is an internal (non-exported) function and the experiment's dynamic import failed; the defense is nonetheless **structurally sound by code reading** and is the same invariant real unzip-overlap CVEs (e.g. CVE-2018-1002204-class) exploit. The gap is that **no existing test constructs an overlapping-entry archive** to prove the walk rejects it — see COV-5.
15. **ed25519 crypto-library audit (code-reading):** signature verification uses Node's built-in `crypto.verify(null, payload, publicKey, sigBytes)` (compatibility.ts, validate.ts, goat-engine-manifest.ts) — i.e. **OpenSSL via Node**, a constant-time, audited implementation. There is **no hand-rolled or third-party ed25519 library** (`tweetnacl`/`@noble/curves`/etc. are absent from `package.json`). The public key is reconstructed via `createPublicKey({ key: publicKeyBytes, format: "der", type: "spki" })` and then **re-exported and compared** (`exported.equals(publicKeyBytes)`) to prove the DER SPKI decodes to exactly the advertised 32 raw bytes — defeating any SPKI-encoding ambiguity. `keyId === sha256(publicKeyBytes)` binds the keyId to the raw key. `@tufjs/canonical-json` is used **only for canonicalization** (a deterministic string transform), never for crypto; `@tufjs/models` `verifyDelegate` delegates to the same `crypto.verify`. All three TUF deps are pinned to **exact** versions (`@tufjs/canonical-json@2.0.0`, `@tufjs/models@5.0.0`, `tuf-js@6.0.0`). Strong crypto posture.
16. **CI workflow security audit (code-reading):** `.github/workflows/test.yml` sets `permissions: contents: read` (least-privilege, no write/pull-request comment token). It triggers on `pull_request` (NOT `pull_request_target` — the dangerous trigger that runs with repo secrets on fork PRs is absent). `actions/checkout` and `actions/setup-node` are **pinned by SHA** (`@34e114876b0b11c390a56381ad16ebd13914f8d5 # v4.3.1`, `@49933ea5288caeca8642d1e84afbd3f7d6820020 # v4.4.0`). The `Add MinGW to PATH` step writes a fixed candidate list to `$GITHUB_PATH` (no PR-controlled interpolation). The `Verify C compiler` step runs `& $cmd --version` where `$cmd` is selected from `$env:RUNNER_OS` (constant), not from PR input — no shell injection. No `secrets.*` are referenced in any step (the workflow only runs build/test, not publish). An ordinary CI compromise on this workflow cannot produce a trusted update (no signing keys, no publish authority — see §9). Solid CI posture.
17. **Interruption-recovery is real-process-proven (test-reading + cross-check):** `interruption.test.ts` spawns a **real child process** (`spawn(process.execPath, ["--import", "tsx", worker, appData, phase])`) running the full `runVerifiedUpdate`, kills it at each of the 15 journal phases, then runs real `recoverInstallation` under a real `acquireUpdateLock` and asserts the installation is **either complete-old or complete-new** (no mixed state), the activation chain is consistent, `validateInstalledActivation` passes, and the release-slot count is exactly 1 or 2. This is **non-mocked, real-process crash + real recovery** — the strongest evidence in the entire suite, and stronger than passes 1–2 implied. The only mocked element *within* that recovery is the `signingRunner`/`healthRunner` inside `validateInstalledActivation` (COV-1/COV-3).

## 2. Executive summary

**No confirmed exploitable vulnerability was found.** The most important structural fact is that **production verified updates are fail-closed in the shipped v0.4.0 build**:

- `src/update/trusted-root.generated.ts` exports `GOAT_TUF_ROOT_BASE64 = null` and `GOAT_TUF_ROOT_SHA256 = null`.
- `src/privacy/release-policy.generated.ts` ships with `updateMetadataOrigin`, `updateArtifactOrigin`, and `embeddedTufRootSha256` all `null`, `engineManifestKeyIds` empty, and `codeSigningIdentities` empty.
- `compiledVerifiedUpdatePolicy` (`policy.ts`) returns `null` when every approved value is absent and throws `GOAT_UPDATE_DISABLED` if any required value is present but incomplete.
- `runUpdateCommand` (`commands/update.ts`) throws `GOAT_UPDATE_DISABLED` when `policy` is `null`.
- `scripts/check-privacy-architecture.mjs` actively fails if production trust roots / origins are non-null in this workspace, and `verify-package.mjs` rejects any packed file outside `dist/` + docs.

Consequence: **no `goat update` flow can run against production trust in v0.4.0**, so there is no live attack surface for the new update subsystem in this release. Every issue below is therefore either a **test-coverage gap** (a claimed protection that is only exercised through mocks), a **documentation mismatch** (acceptance-matrix status overstated relative to evidence), or a **defense-in-depth recommendation** — not a confirmed exploitable hole.

The architecture itself is strong: TUF-threshold metadata authentication with monotonic revocations and version/digest floors; canonical-JSON parsing that rejects duplicate keys and non-canonical forms before any signature is interpreted; held-file-descriptor download with post-sync re-hash (TOCTOU mitigation); a hardened ZIP preflight that rejects traversal, device names, symlinks/hardlinks/junctions, data descriptors, prepended/appended bytes, and enforces entry/size/ratio limits; exact-match archive verification before any permission is granted; activation as an ordered durable transaction with an append-only hash-chained journal; rollback material that is independently re-verified; and an anti-downgrade floor that automatic rollback never lowers. My hostile experiments confirmed the junction, duplicate-key, case-collision, and trailing-suffix defenses behave as documented.

The release-gate blocker is **not** a vulnerability — it is that the **real platform code-signing verification path (Windows Authenticode via PowerShell; macOS `codesign` + `spctl`) is never executed by any test**: every activation/rollback/recovery test injects a mocked `signingRunner`/`healthRunner` that returns canned results. The acceptance matrix marks the corresponding criteria `✅`. Per this review's standard ("a mocked test is not sufficient when production safety depends on actual … process behavior"), that is a mandatory-hostile-test gap that must be closed before production trust is ever enabled. Because production updates are disabled today, this gates *enabling* the feature, not *shipping* the fail-closed launcher.

## 5. Test-coverage gaps

### COV-1 — Real platform code-signing verification is never exercised (release-gating)

- **Severity:** High (coverage gap; release-gating)
- **Confidence:** High
- **Affected files / line ranges:**
  - `src/update/code-signing.ts` — `verifyWindowsAuthenticode` (~L80-130), `verifyMacDeveloperId` (~L132-180), `defaultRunner` (~L190-210), `POWERSHELL_SIGNATURE_SCRIPT` (~L40-46)
  - `src/update/activation.ts` — `activateCandidate` calls `verifyPlatformCodeSignature` (~L120-128) and `validateInstalledActivation` (~L150-160)
  - `src/update/health.ts` — `runEngineHealthCheck`, `defaultRunner` (~L40-90)
  - `test/v0.4.0-update/update-bundle-fixture.ts` — `signingRunner` (~L366-395) and `healthRunner` (~L397-404) return canned `{status:0,…}` results
  - `src/update/code-signing.test.ts`, `src/update/health.test.ts` — assert against mocked runners
- **Violated invariant (as claimed):** Acceptance-matrix X4 ("Files are non-executable until verification is complete"), I4 ("No remote bytes execute before all authentication and compatibility checks"), I12 code-signing component, and N2/N3 — all marked `✅` with evidence pointing at tests that mock the verification.
- **Preconditions:** A build in which production trust is enabled (future release). In v0.4.0 as shipped, production updates are disabled, so this is not exploitable today.
- **Attack / failure sequence:** When production trust is later enabled, an attacker who can influence the engine archive (CDN/proxy compromise, or a build/signing mistake) relies on the code-signing gate to be caught. That gate's correctness — PowerShell `Get-AuthenticodeSignature` JSON shape, `GetCertHashString('SHA256')` casing, `status === "Valid"` semantics; macOS `codesign --display` `TeamIdentifier=`/`Authority=` line parsing and `spctl --assess` acceptance — is currently validated only against mocked strings. A parsing mismatch (e.g., authority line ordering, certificate-thumbprint case, `spctl` non-zero on ad-hoc signatures) would not be detected by the suite.
- **Impact:** If a real-platform parsing mismatch exists, a malformed or incorrectly-signed engine could be accepted (or, symmetrically, a valid one rejected) at activation. Not exploitable in v0.4.0 (fail-closed).
- **Reproduction / supporting evidence:** `grep` across `src/update/*.test.ts` and `test/v0.4.0-update/update-bundle-fixture.ts` shows all activation/rollback/recovery tests pass `runSigningCommand`/`runHealthCommand` mocks; no test spawns the real `powershell.exe`/`codesign`/`spctl` against a compiled binary. My local probe (`.hostile-codesign-exp.mjs`) could not compile `fixture-engine.c` (no C compiler), matching the skipped native health test.
- **Smallest safe remediation:** Add a native code-signing test (gated on tool availability, `context.skip` when absent, like the native health test) that: (a) compiles the fixture engine; (b) runs `verifyPlatformCodeSignature` with the **default** runner against the **unsigned** binary and asserts `GOAT_UPDATE_CODE_SIGNATURE_INVALID`; (c) on platforms where a test signing identity/certificate is available in CI, signs the fixture and asserts acceptance with the matching approved identity and rejection with a non-matching one. Mirror for `runEngineHealthCheck` is already present (`health.native.test.ts`) but should also assert rejection on a binary whose `--version` output is wrong.
- **Required regression test:** Native (non-mocked) `verifyPlatformCodeSignature` rejecting an unsigned compiled fixture on Windows and macOS; accepting/rejecting per approved-identity match.

### COV-2 — "Locked Windows executable does not corrupt activation" (I12) is untested

- **Severity:** Medium (coverage gap)
- **Confidence:** High
- **Affected files / line ranges:** `src/update/activation.ts` (`activateCandidate` rename ~L100-115, `cleanupSupersededSlots` ~L135-175); `src/update/recovery.ts`; acceptance-matrix I12 marked `✅` with evidence `activation.test.ts`.
- **Violated invariant (as claimed):** I12 — "A locked Windows executable does not corrupt activation."
- **Preconditions:** Windows; the currently-active engine binary is held open (running) while a new update activates and cleanup attempts to remove the superseded slot.
- **Attack / failure sequence:** `activateCandidate` places the new release into a **new unique** slot (`assertAbsent` + `expectedSlotName`), so the atomic `rename` target is not the locked file — good by design. The locked-exe risk is in `cleanupSupersededSlots`, which `rm`s the old slot with `maxRetries: 1` and pushes failures to `deferredCleanupPaths` rather than corrupting state. This design is sound, but **no test holds the active engine executable open** during activation/cleanup to prove the deferred-cleanup path actually triggers and leaves both the new activation and the (still-locked) old slot consistent. `grep` for `locked`, `EPERM`, `EACCES`, `in use`, `running.*engine` in `activation.test.ts`/`recovery.test.ts`/`rollback.test.ts` returns no relevant hit.
- **Impact:** A latent Windows-specific cleanup/activation inconsistency could go unnoticed. Not exploitable in v0.4.0 (fail-closed).
- **Smallest safe remediation:** A Windows-native test that spawns/holds the active engine executable open, runs a full `runVerifiedUpdate` to a new release, and asserts: activation succeeds, the old slot is either removed or reported in `deferredCleanupPaths`, and `loadActivationChain` + `validateInstalledActivation` remain consistent.
- **Required regression test:** Windows locked-executable activation + deferred-cleanup consistency test.

### COV-3 — macOS `codesign`/`spctl` real-output parsing unverified

- **Severity:** Medium (coverage gap; cross-platform)
- **Confidence:** High
- **Affected files / line ranges:** `src/update/code-signing.ts` `verifyMacDeveloperId` (~L132-180) — parses `TeamIdentifier=` and `Authority=` lines from `codesign --display --verbose=4` stderr and checks `authorities[0]` against the approved authority; `spctl --assess --type execute`.
- **Violated invariant (as claimed):** I4 / X4 for the darwin platform.
- **Preconditions:** macOS. This review was performed on Windows, so I could not execute the darwin verification tools.
- **Attack / failure sequence:** Same class as COV-1: the `TeamIdentifier=`/`Authority=` line parsing and `authorities[0]` ordering assumption, and `spctl` exit semantics, are validated only via `signingRunner` mocks in `code-signing.test.ts`. Real `codesign --display --verbose=4` output can vary across macOS versions; if the first `Authority=` line is not the leaf certificate, the `authorities[0]` check could mis-accept or mis-reject.
- **Impact:** Latent darwin code-signing acceptance error. Not exploitable in v0.4.0 (fail-closed).
- **Smallest safe remediation:** Native macOS test (skip if `codesign`/`spctl` absent) verifying rejection of an unsigned/ad-hoc-signed fixture and acceptance logic against a Developer-ID-signed fixture where available in CI.
- **Required regression test:** Native darwin `verifyPlatformCodeSignature` rejection/acceptance test.

### COV-5 — Overlapping-entry / contiguous-range ZIP defense is untested by a hostile archive

- **Severity:** Low (coverage gap)
- **Confidence:** High
- **Affected files / line ranges:** `src/update/archive.ts` — `preflightArchive` contiguous-range walk (~L110-125: `ranges` sorted by `localStart`, `expectedStart === range.localStart` check, `expectedStart === eocd.centralDirectoryOffset` final check); `src/update/archive.test.ts` (no overlapping-entry case).
- **Violated invariant (as claimed):** The design rejects overlapping local-file-header regions (the zip-overlap attack class). `archive.test.ts` covers traversal, symlinks, hardlinks, data descriptors, prefix/suffix bytes, comments, local-name mismatch, deflate ratio bombs, device names, and case collisions — but does **not** construct an archive where one entry's local-file-header + data is embedded inside another entry's data region so that two entries decode overlapping bytes to different file contents.
- **Preconditions:** A build in which production trust is enabled (future release). In v0.4.0 as shipped, production updates are disabled, so this is not exploitable today.
- **Attack / failure sequence:** An attacker who controls the archive bytes (CDN/proxy compromise) crafts a zip where entry A's data contains a valid local-file-header + payload for entry B, and B's central-directory entry points into A's data range. A naive extractor that reads entries by central-directory offset would extract A and B from overlapping bytes, yielding two different files from one byte range (confusion / smuggling). GOAT's `preflightArchive` rejects this because the contiguous-range walk requires each entry's `[localStart, dataEnd)` to abut the previous one with no overlap and no gap, terminating exactly at the central directory. The defense is structurally sound; it is simply not yet proven by a hostile test.
- **Impact:** If the contiguous-range walk had an off-by-one or boundary bug, an overlapping-entry archive could bypass the signed-contents binding. Not exploitable in v0.4.0 (fail-closed), and the walk reads correctly, but unproven.
- **Reproduction / supporting evidence:** `grep` for `expectedStart` / `localStart` / `centralDirectoryOffset` in `archive.ts` confirms the walk; `grep` for `overlap` / `contiguous` / `localStart` in `archive.test.ts` returns no overlapping-entry test. My hostile probe (EXP14) could not execute because `preflightArchive` is non-exported.
- **Smallest safe remediation:** Add an `archive.test.ts` case that builds an archive with an embedded local-file-header (entry A's data bytes crafted to be a valid local header + payload for entry B, B's central offset pointing into A's data) and asserts `extractVerifiedArchive` rejects it (expected `GOAT_UPDATE_ARCHIVE_INVALID`). Export `preflightArchive` from `archive.ts` for testability, or test via `extractVerifiedArchive` (which calls it).
- **Required regression test:** Overlapping-entry / embedded-local-header hostile archive rejected by the real `extractVerifiedArchive`.

### COV-4 — Native health test silently skips when no C compiler is present

## 7. Defense-in-depth recommendations

These are not findings (no evidence of a defect); they are hardening suggestions. Most apply when production trust is enabled; D-7 applies now, while the legacy engine path is still reachable in the fail-closed build.

1. **D-1 — Tighten `cleanupSupersededSlots` slot-name rejection.** `cleanupSupersededSlots` (`activation.ts` ~L155) throws `GOAT_UPDATE_RECOVERY_REQUIRED` for any malformed slot name, which is safe, but it scans all three channels' `releases/` dirs. Consider bounding the total directory walk (it already caps via the 2-keep rule) and logging the rejected name to a local-only diagnostic (never to network) to aid recovery. No change to security posture.
2. **D-2 — Pin `@tufjs/models` / `tuf-js` behavior.** TUF threshold verification depends on `@tufjs/models` `verifyDelegate`. The repo patches several dependencies (`patches/`). Confirm `@tufjs/models` is pinned and its `verifyDelegate` semantics (threshold, keyid matching) are covered by `trust.test.ts`'s "real TUF thresholds authenticate one consistent channel metadata set" — which it is. No action unless upgrading.
3. **D-3 — `metadata-client.ts` root-walk 404 handling.** `readOptionalRoot` treats only `NetworkRequestError` with `statusCode === 404` as "no more roots." A server that returns 404 with a non-`NetworkRequestError` shape, or a 200 with empty body, would not loop forever (bounded by `MAX_ROOT_UPDATES_PER_CHECK=32` and `MAX_SEQUENTIAL_ROOT_BYTES`), but consider asserting the 404 path returns a body within `METADATA_NETWORK_LIMITS.maxBytes` (already enforced). No defect found.
4. **D-4 — `downloadVerifiedArtifact` content-length header trust.** The signed `target.length` is the authority; the `Content-Length` header is only a pre-check (`validateResponse` rejects >`maxBytes`; `downloadVerifiedArtifact` rejects header ≠ `target.length` if present). Streaming enforces `bytesWritten + chunk > target.length` and final `bytesWritten !== target.length`. Correct. No action.
5. **D-5 — Lock release on Windows.** `lock.ts` releases by `rename(lockPath → releasePath)` then `rm`. On Windows, if the lock directory's `owner.json` is held open, `rename` may fail; the release path re-reads and asserts `sameOwner` before rename, throwing `LOCK_INVALID` on mismatch. This is safe (fail-closed) but could strand a lock if the owning process died mid-release; `acquireUpdateLock`'s stale-owner recovery handles this. No defect.
6. **D-6 — `allowUnsignedDevelopment: true` in the shipped policy is unreachable as a download-trust bypass (defense-in-depth, not a vulnerability).** Full reachability walk-through:
   - (a) `assertLauncherReleasePolicy` (`release-policy.ts`) **requires** `allowUnsignedDevelopment: true` for any non-production channel and **forbids** it for production (`!policy.distribution.allowUnsignedDevelopment` throws `production_release_blocked` in the production branch; the non-production branch requires `allowUnsignedDevelopment` to be `true`). The shipped v0.4.0 build is the `internal` channel, so the flag being `true` is the **expected and enforced** state, not a misconfiguration.
   - (b) The unsigned-development manifest path in `validateManifestTrust` (`validate.ts`) only accepts `signature.status === "unsigned-development"` when **both** `manifest.releaseChannel === "dev"` **and** `trustPolicy.allowUnsignedDevelopment` hold.
   - (c) `validateManifestAgainstResolution` rejects any manifest whose `releaseChannel` ≠ the resolved engine's `releaseChannel`, so a `dev`-channel manifest cannot be matched against a `stable`/`beta` resolved engine.
   - (d) The separate `developmentOverride` branch additionally requires `resolved.source === "development"` and `resolved.releaseChannel === "dev"`.
   - (e) Both paths require an attacker to already write a manifest + binary into the install directory — i.e., local write/code-execution privilege on the victim machine — which is **outside the download-trust boundary** and is not a privilege escalation.
   - (f) Critically, the legacy `resolveLegacyEngine` path (the one actually taken in the shipped fail-closed build — see §2/§9) reads a **locally installed** engine manifest; it does **not** fetch over the network, so `allowUnsignedDevelopment` cannot be reached by a remote attacker through the update flow.
   - **Conclusion:** this flag does not enable a remote/unsigned-manifest bypass in the shipped build; it is correctly gated out of production and correctly scoped to `dev`-channel local development. **Recommendation (defense-in-depth only):** when production trust is enabled, have `check-privacy-architecture.mjs` assert the production policy's `allowUnsignedDevelopment: false` (it already asserts null production origins; extend it to assert the production-branch invariants from `assertLauncherReleasePolicy`).

7. **D-7 — Legacy v1 manifest parser (`validate.ts`) accepts duplicate object keys (defense-in-depth, not a vulnerability).** As proven by experiment 11 above, the legacy `parseManifest` uses `JSON.parse` which silently resolves duplicate JSON object keys last-wins, whereas the v0.4 `parseCanonicalJson` rejects duplicate keys outright (`GOAT_UPDATE_MANIFEST_INVALID`). This divergence is **not exploitable** because the ed25519 signature in `validateManifestTrust` is verified over the re-serialized canonical form (`canonicalEngineManifestPayload`), and as analyzed in EXP11 either (a) a value-changing duplicate alters the canonical bytes → signature fails (fail-closed), or (b) a value-preserving duplicate leaves the legitimate value in place → no hostile value is honored (there is no third case). The divergence is nonetheless a parser-hardening weakness: the legacy path relies on the signature as the sole defense against duplicate-key ambiguity, while the v0.4 path rejects ambiguity before the signature is interpreted. **Recommendation (defense-in-depth only):** while the legacy `resolveLegacyEngine` path is still reachable (i.e., until production trust is embedded and `inspectInstalledEngine` becomes the live path), replace `JSON.parse` in `parseManifest` with a duplicate-key-rejecting parser (e.g., reuse `parseCanonicalJson`'s key-scanning logic, or a `reviver`-based detector) so the legacy path matches the v0.4 invariant that manifests are canonical before signature verification. No production trust is required for this hardening and it does not change v0.4.0's fail-closed posture.
8. **D-8 — ed25519 uses Node `crypto.verify` (OpenSSL, constant-time), not a hand-rolled library (strength, no defect).** As audited in EXP15, all ed25519 verification routes through Node's built-in `crypto.verify`; `package.json` contains no `tweetnacl`/`@noble`/`@stablelib` hand-rolled crypto. `@tufjs/canonical-json` is canonicalization-only. The public key is re-exported and byte-compared to defeat SPKI-encoding ambiguity, and `keyId === sha256(publicKeyBytes)`. The three TUF deps are pinned to exact versions. **Recommendation (defense-in-depth only):** when upgrading any TUF dep, re-run `trust.test.ts`'s real-threshold suite and confirm `verifyDelegate` still routes through `crypto.verify` (not a bundled JS fallback). No action for v0.4.0.
9. **D-9 — `syncDirectory` is best-effort on Windows (known limitation, no defect).** `durable.ts` `syncDirectory` swallows `EISDIR`/`EPERM`/`EACCES` on `win32` (directory-handle `fsync` is not uniformly supported on Windows) and returns silently. Directory-rename durability on Windows therefore relies on the atomic `rename` plus file-level `handle.sync()` (which `writeImmutableFile` performs before close) rather than parent-directory fsync. This is the standard Node-on-Windows limitation, not a GOAT defect: every journal/activation/receipt/state record is `writeImmutableFile`'d with file-level `sync()` + temp-file-rename + post-rename read-back verification. **Recommendation (defense-in-depth only):** none for v0.4.0; if Windows ever offers a durable directory-flush primitive, adopt it. State this assumption when relying on Windows activation durability.
10. **D-10 — `readImmutableFile` is TOCTOU-protected (strength, no defect).** `durable.ts` performs lstat → open("r") → fstat → compare `dev/ino/nlink/size/isFile/isSymbolicLink` → readFile → fstat → re-compare `dev/ino/size`, plus a `realpath` equality check (rejects symlinks/junctions/reparse points where canonical ≠ path). An attacker who swaps the file between lstat and open is caught by the fstat-vs-lstat comparison; a swap during the read is caught by the after-read fstat. This protects every journal, activation-record, receipt, state, and lock-owner read. No defect; noted because it is the foundation of the offline-state integrity and was not called out in passes 1–2.
11. **D-11 — `authenticateInstalledReceipt` intentionally skips expiry for installed receipts (correct TUF posture, no defect).** `trust.ts` documents: expiry prevents *accepting an update from the network*, but does not by itself *revoke an already-authenticated installed engine*. Installed receipts are re-authenticated with `enforceExpiration: false`, but **current revocations are still applied** (`assertNoCurrentlyRevokedSigner`, `assertRevocationsMonotonic`, version/digest floors). This is the correct TUF design (offline installed engines remain usable after metadata expiry; only network refresh is gated). No action.
12. **D-12 — Recovery-of-last-resort (receipt reconstruction) requires full TUF re-authentication (strength, no defect).** `reconstructStateFromReceipts` (receipt.ts) re-loads every persisted receipt and re-runs each through `TufTrustStore.authenticateInstalledReceipt` (root-walk, threshold, delegation, version/digest floors, monotonic revocations), then cross-checks the reconstructed state against the activation chain. A corrupt state directory is **quarantined** (renamed to a random name under `updates/quarantine/`) and rebuilt from receipts. An attacker who can write a forged receipt must still pass the full TUF trust-store authentication (signing keys, root threshold, delegation) — recovery state is **not** attacker-controllable without the signing keys. This closes the "recovery state controllable by an attacker" checklist item. No defect.

**Third-pass structural note.** The deepest result of this pass is that the update subsystem's attack surface is **structurally gated to zero in v0.4.0** by a single invariant: *no network fetch, no archive extraction, and no activation can occur unless a production `VerifiedUpdatePolicy` is compiled*, and `compiledVerifiedUpdatePolicy` returns `null` when every production value is absent (the shipped state). Because the policy also binds the embedded TUF root hash, both origins, the manifest key IDs, and the platform code-signing identities together (any inconsistency throws `GOAT_UPDATE_DISABLED`), there is no partial-enablement window. The layers above that gate (TUF threshold auth, canonical-JSON parsing, held-file download, hardened ZIP preflight, exact-match archive verification, ordered durable activation, append-only hash-chained journal, anti-downgrade floor, rollback re-verification, receipt-based recovery) are defense-in-depth that become the live attack surface only when production trust is later embedded — which is exactly when COV-1/COV-2/COV-3/COV-5 must be closed.

**Important context for the verdict.** Every "Yes" above is a **coverage gap on a feature that is fail-closed in the shipped v0.4.0**, not a confirmed or likely exploitable vulnerability. There is no production attack surface for the *new update subsystem* in this release: `goat update` throws `GOAT_UPDATE_DISABLED`. Separately, because `compiledVerifiedUpdatePolicy` returns `null` in production, `updatePolicy?.activation` is `undefined`, so `launchEngine`'s verified-install branch (`if (!options.resolvedEngine && options.installedUpdatePolicy)` → `inspectInstalledEngine`) is **not taken** in the shipped build; the launcher falls back to `resolveLegacyEngine` (the pre-v0.4 engine resolution path, out of primary scope). Thus `inspectInstalledEngine` and the entire v0.4 verified-activation read path are unreachable until a production update policy is embedded. The gaps below gate **enabling production trust in a future release**, and the acceptance matrix should reflect them (DOC-1) until native code-signing evidence exists.

**Additional gate evidence (cross-checked this pass).**
- **"Race two updater processes"** — has **real, non-mocked** evidence: `src/update/lock.test.ts` `concurrentUpdaterAllowsExactlyOneOwner` issues multiple concurrent `acquireUpdateLock` calls and asserts exactly one succeeds while the rest reject with `GOAT_UPDATE_BUSY`; subsequent `assert.rejects` calls confirm a second acquire against a held lock is denied. The lock is a real `fs.open`-based exclusive file (fail-closed on `EEXIST`/`EPERM`). This gate item is satisfied on the platform reviewed (win32).
- **"CI matrices that claim tests they do not execute"** — `.github/workflows/test.yml` declares a matrix of `windows-latest` + `macos-latest` on Node 24, with steps `typecheck`, `npm test`, `verify:package`, plus a Windows-only `choco install mingw`. It does **not** declare any `codesign`/`spctl`/`authenticode` step, so it makes **no false claim** of running native code-signing verification. The gap is that `npm test` itself relies on mocked runners (COV-1/COV-3); the CI does not add a native code-signing step on top. So this specific anti-pattern (a matrix *claiming* a test it doesn't run) is **not present**, but the underlying coverage gap remains and is captured by COV-1/COV-3.
