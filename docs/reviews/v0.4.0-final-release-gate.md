# GOAT v0.4.0 Final Release-Gate Review

- Review date: 2026-07-28
- Repository: `Kyle333-glitch/goatcli`
- Candidate branch: `feat/v0.4.0-packaging-updates`
- Candidate version: `0.4.0` — Packaging and verified updates
- Review type: fresh, full-diff security and release-gate review
- Threat boundary: the updater is treated as a remote-code-execution boundary

## Executive result

The release gate is closed. A fresh implementation review found four new high-impact defects in authenticated trust-state persistence, update serialization, interruption recovery, and verification-to-activation binding. It also found several mandatory hostile tests that either do not exist or do not reach the production guard claimed by their names. The current candidate has no pull-request CI evidence, lacks native coverage for two supported OS/architecture tuples, still has no native code-signing or Windows locked-executable proof, ships documentation that contradicts v0.4 behavior, and fails its declared formatting/publish gate.

The fact that compiled production trust values are currently null and `goat update` consequently fails closed does not waive these blockers. This review evaluates the implementation intended to become the trusted update boundary.

## Scope, baseline, and method

`HEAD` is `22fc9d793f3c0b6038b19a8755d9260eaac54590`, shared with the local v0.3.2 implementation branch. The v0.4 candidate exists as the complete working tree on `feat/v0.4.0-packaging-updates`: tracked modifications plus untracked updater source, tests, fixtures, and documents. That working tree was reviewed against `HEAD`; it is not represented by any current remote commit.

The review covered:

- the complete tracked diff and every untracked v0.4 source/test/document file;
- TUF/canonical-JSON authentication, target selection, download, archive, activation, rollback, recovery, CLI, packaging, and CI;
- actual test assertions and the production functions they reach, rather than test names alone;
- temporary production-code probes using loopback HTTPS and temporary app-data directories for state-timing, timeout, streaming-size, lock-race, interruption, and substitution behavior;
- the dry-run npm payload and installed production dependency graph;
- the security design, acceptance matrix, earlier review, and remediation record as claims to re-test, not as evidence of resolution.

No implementation code, test, workflow, package metadata, commit, branch, or remote state was changed. This report is the only file updated.

## Remaining findings

### F-01 — High: authenticated trust state is lost before selection succeeds

`runLockedUpdate` authenticates all metadata and computes `authenticated.nextState` at `src/update/updater.ts:213-221`. It then selects a target at `src/update/updater.ts:223-237` and persists a receipt/state only at `src/update/updater.ts:244-273`. The catch at `src/update/updater.ts:370-375` cleans up and rethrows without persisting authenticated metadata.

Consequently every selection-stage failure discards newly authenticated root/version/digest floors, trusted time, and key/artifact/release revocations. This includes no matching tuple, ambiguity, revoked target, launcher incompatibility, downgrade, same-floor replay, and malformed/mismatched target paths (`src/update/selection.ts:83-163`). `findOrPersistReceipt` failures also precede the state append.

Launch-time validation derives its effective revocations only from the old persisted state (`src/update/installed.ts:28-49`, `src/update/recovery.ts:421-443`). A real loopback/TUF probe installed signed stable v1, authenticated signed v2 that revoked the active inner-manifest key and artifact but had no current-platform target, and then inspected/replayed v1. The result was:

```json
{"v2Failure":"GOAT_UPDATE_TARGET_NOT_FOUND","afterV2MetadataVersion":1,"afterV2Revocations":[],"revokedEngineStillAccepted":true,"replayedV1Status":"already-current","afterReplayMetadataVersion":1}
```

This is not a mock-error assertion: it exercised production HTTPS transport, TUF signing/authentication, `runVerifiedUpdate`, persistent state loading, and installed-engine validation. No existing end-to-end test covers this timing.

### F-02 — High: stale-lock recovery is concurrently entered

At `src/update/lock.ts:88-96`, every contender that observes a dead owner invokes `recoverStaleTransaction` while the stale lock still exists. Exclusive quarantine/rename ownership is attempted only afterward at `src/update/lock.ts:100-113`. The comment that the stale lock excludes every new updater is therefore false for recovery callbacks.

A two-contender production-function probe recorded `entered: 2`; one acquisition fulfilled and the other rejected, but both recovery callbacks ran concurrently. Recovery writes journals/state (`src/update/recovery.ts:301-306`) through exclusive durable-record creation (`src/update/durable.ts:86-105`), so concurrent callbacks can race/fork recovery or force a permanent fail-closed state. Tests cover live-lock contention and one stale contender only (`src/update/lock.test.ts:13-60`).

### F-03 — High: activation record and journal have an unsafe crash gap

The activation record becomes durable at `src/update/activation.ts:176-192`. Only afterward does the observer append `commit-activation` to the journal (`src/update/activation.ts:193`, `src/update/updater.ts:330-333`). A process death between those operations leaves the journal at `validate-provisional-slot` while the activation chain already references the new slot.

Recovery interprets the pre-commit journal as an uncommitted slot and tries removal (`src/update/recovery.ts:280-295`), then refuses because the activation chain references it (`src/update/recovery.ts:319-323`). A production-code probe reproduced `GOAT_UPDATE_RECOVERY_REQUIRED` with activation generation 1 and a journal ending at `validate-provisional-slot`.

The 15-phase crash worker terminates only after each observer transition has already persisted its journal record (`src/update/interruption.test.ts:33-43`, `test/v0.4.0-update/update-crash-worker.ts:82-85`). The recovery test around activation commit has no incomplete journal (`src/update/recovery.test.ts:160-193`). The vulnerable internal boundary is therefore absent from the suite.

### F-04 — High: verified provisional bytes can be substituted before activation commit

Final tree verification, compatibility, platform signature verification, and the health check finish at `src/update/activation.ts:149-173`. The function then awaits `provisionalSlotValidated` at line 174 and appends the activation record at lines 176-192 without re-opening/re-hashing the exact files or otherwise making the slot immutable.

A production-function probe replaced the executable in the observer window. `activateCandidate` returned `committed`; subsequent `validateInstalledActivation` rejected it with `GOAT_UPDATE_ARCHIVE_CONTENT_MISMATCH`. Later launch validation prevented demonstrated execution, but the activation record still committed an identity for bytes different from those verified. This directly violates the requested verification-to-activation invariant. `src/update/activation.test.ts:21-75` calls the slot immutable but contains no substitution attempt.

### F-05 — Release-blocking hostile-test gaps and misleading assertions

- Sequential TUF root rotation has no test with non-empty `sequentialRoots`. `src/update/metadata-client.test.ts:11-39` asserts zero roots, while the acceptance matrix incorrectly cites a channel-mutation signature test as root-rotation evidence. A positive dual-threshold production probe succeeded, but skipped versions, old-only/new-only thresholds, revoked rotation keys, and root-count/byte limits are untested (`src/update/trust.ts:229-257`, `src/update/metadata-client.ts:38-61`).
- `src/update/network.test.ts:86-101` sets header timeout 20 ms, total timeout 40 ms, and withholds headers 80 ms. Only the header timer can win. Total-body and idle-body guards (`src/update/network.ts:84-97,127-140,267-277`) have no hostile test. Probes showed both remain bounded, but the total path surfaced as retryable `GOAT_UPDATE_NETWORK_FAILED`/`ECONNRESET`.
- The oversized metadata test always receives `Content-Length`, so it reaches only `src/update/network.ts:249-252`, not the streaming guard at lines 165-172. The artifact length test likewise supplies an intentionally wrong header and rejects at `src/update/download.ts:48-54`, never the streamed-byte guard at lines 56-68. Chunked probes showed both guards currently fail closed, but the mandatory tests are absent.
- `src/update/archive.test.ts:129-164` has no case that exceeds `maxTotalExpandedBytes` while every entry remains below its individual limit. The count case would still produce the same generic limit error from signed-manifest cardinality mismatch if the explicit entry-count check were removed, so it is not a discriminating assertion for that guard.

### F-06 — Native platform safety remains unproved

`src/update/code-signing.test.ts` injects `runCommand` and asserts mocked PowerShell, `codesign`, and `spctl` outputs. It never executes native Authenticode or Apple verification. No test holds a running Windows executable open while update activation/cleanup proceeds. The local native fixture test skipped because no C compiler was available. These are mandatory hostile/native cases, not optional evidence deferred by null production trust.

### F-07 — CI/native architecture evidence is incomplete

The supported tuple is Windows/macOS × x64/arm64 (`src/update/schema.ts:16-18`, `README.md:9-12`). The workflow has only `windows-latest` and `macos-latest` (`.github/workflows/test.yml:19-27`) and no architecture dimension. GitHub currently maps those standard labels to Windows x64 and macOS arm64; native `windows-11-arm` and `macos-15-intel` runners are available but unused ([GitHub-hosted runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)). Simulated architecture strings in unit tests are not native execution evidence.

All v0.4 changes are uncommitted, so no remote workflow can represent this candidate. The GitHub connector found only run `30163348950` on `22fc9d7`; that was the older v0.3.2 privacy workflow, not this implementation.

### F-08 — Shipped documents contradict actual behavior

`README.md:5,26,30,41,44` and `PRIVACY.md:3,15,28,42,46,48,71` repeatedly say v0.3.2 has no download/update/self-update path and describe the old launcher-only version output. The implementation owns expanded `goat version` and verified `goat update` at `src/cli.ts:113-174`, `src/commands/update.ts:22-45`, and `src/commands/version.ts:24-90`. Both stale documents ship in the npm payload. The package verifier checks paths/presence, not semantic accuracy.

### F-09 — Release permission separation is not demonstrated

Ordinary CI is appropriately least-privileged: `.github/workflows/test.yml:15-16` grants only `contents: read`, uses `pull_request` rather than `pull_request_target`, references no secrets, and has no signing/publish/upload step. This verifies that ordinary CI cannot itself obtain every release privilege.

It does not prove that build, platform signing, artifact publishing, TUF metadata signing, and manifest publishing are held by separate authorities. The repository contains no release workflow or runbook that identifies those principals. `package.json` provenance metadata is not permission-separation evidence. The gate must remain closed until external release-process evidence is supplied.

### F-10 — The declared publish gate fails and CI omits it

`npm run format:check` fails on 52 files, including most new updater source/tests. `package.json:29` places that check first in `prepublishOnly`. Current CI runs typecheck, tests, and package verification only (`.github/workflows/test.yml:72-82`), so it can report success while the declared publish gate is failing.

### F-11 — Lower-severity package/CI hardening observations

- `scripts/verify-package.mjs:59-86` allowlists paths but does not scan allowed `dist/` files for private-key/secret markers or unexpected `.pem`, `.key`, `.node`, or `.exe` content. The actual inspected payload was clean, so this is a prevention-gap rather than a present secret leak.
- `tuf-js` is a direct production dependency but has no source/test import; the used canonicalization package is `@tufjs/canonical-json`. The unused dependency unnecessarily enlarges supply-chain surface.
- Windows CI installs an unversioned Chocolatey MinGW package and Node is a floating major (`.github/workflows/test.yml:35,42-45`), reducing native-test reproducibility. Ordinary CI has no release credentials, which limits impact.
- The untracked repository-root `nul` file contains command-error junk. It is excluded from the npm payload but is not release-worktree hygiene.
