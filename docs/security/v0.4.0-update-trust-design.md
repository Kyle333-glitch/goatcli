# GOAT v0.4.0 — Verified Update Trust Design

## Overview

The GOAT launcher v0.4.0 introduces a verified, privacy-bounded update mechanism. Updates are delivered over HTTPS but are not trusted because of TLS; every byte that affects the installation is authenticated before it is used.

## Threat Model

- The metadata and artifact origins are approved at build time.
- TLS provides transport privacy and integrity against passive attackers, not code-trust.
- An attacker may compromise the CDN, DNS, or a proxy and serve malicious metadata, artifacts, or both.
- The launcher must fail safely in all such cases.

## Trust Architecture

### Embedded Root

A TUF root is embedded in the launcher binary. Its SHA-256 is compiled into the binary and checked at startup. If the embedded root is missing or inconsistent, verified updates are disabled.

Implementation: `src/update/policy.ts:compiledVerifiedUpdatePolicy`, `src/update/trust.ts:TufTrustStore` constructor.

### Metadata Authentication

All top-level metadata (root, timestamp, snapshot, targets) and the channel target file are signed according to TUF thresholds. The launcher:

1. Parses the embedded root (`TufTrustStore` constructor).
2. Authenticates sequential root updates if provided (`TufTrustStore.applySequentialRoots`).
3. Authenticates timestamp → snapshot → targets → channel (`TufTrustStore.authenticateInternal`).
4. Verifies version and digest floors to prevent rollback (`assertMetadataFloors`).
5. Applies monotonic revocation sets (`assertRevocationsMonotonic`).

Tests: `src/update/trust.test.ts` covers threshold signatures, unknown/revoked keys, expired metadata, snapshot mix-and-match, and revocation rollback.

### Artifact Selection

After metadata authentication, the launcher selects the artifact matching the current platform, architecture, launcher version, and channel. Revoked artifacts and downgrade attempts are rejected.

Implementation: `src/update/selection.ts:selectAuthenticatedArtifact`.
Tests: `src/update/selection.test.ts` covers platform/architecture/channel mismatches, launcher compatibility, and anti-downgrade floors.

### Download and Hold

Artifacts are downloaded to an exclusive temporary file. The downloaded content is verified against the authenticated target length and SHA-256 while streaming. After the initial hash is verified, the file is re-read from the held file descriptor and re-hashed to detect TOCTOU. The artifact handle is kept open so a pathname swap cannot affect the bytes fed to extraction.

Implementation: `src/update/download.ts:downloadVerifiedArtifact`, `HeldVerifiedArtifact`, `assertHeldArtifactUnchanged`.
Tests: `src/update/download.test.ts` covers interrupted downloads, hash mismatches, pathname replacement, and signed length enforcement.

### Extraction

Extraction uses a hardened ZIP parser with strict limits:

- Max entries, max single/total expanded size, max compression ratio (`extractVerifiedArchive`).
- Rejection of traversal, dot segments, duplicate normalized paths, and Windows device names (`validateArchivePath`).
- Exact match against the signed content manifest (`verifyStagedArchive`).
- Files are extracted non-executable; permissions are finalized only after verification (`finalizeStagedPermissions`).

Implementation: `src/update/archive.ts:extractVerifiedArchive`.
Tests: `src/update/archive.test.ts` covers hostile paths, device names, symlink/hardlink escapes, data descriptors, and resource limits.

### Activation

Activation is performed as a sequence of durable steps recorded in a transaction journal:

1. Prepare rollback by validating the existing installation.
2. Finalize staged permissions and verify code signatures.
3. Run a health check against the staged executable.
4. Move the staged tree into a versioned release slot.
5. Commit the activation record.
6. Clean up superseded slots.

Implementation: `src/update/activation.ts:activateCandidate`, `src/update/journal.ts:appendJournalTransition`.
Tests: `src/update/activation.test.ts`, `src/update/journal.test.ts`.

Each step can be recovered after a crash because the journal and activation chain are append-only. The crash-worker fixture in `test/v0.4.0-update/update-crash-worker.ts` terminates the process at each durable boundary and verifies that recovery leaves a complete old or new installation.

### Rollback and Recovery

If activation fails after the provisional slot is placed, recovery re-verifies the prior activation and removes partial state. Rollback material is independently re-verified from persisted receipts. The anti-downgrade floor is never lowered by a rollback.

Implementation: `src/update/recovery.ts:recoverInstallation`, `src/update/rollback.ts:performAutomaticRollback`.
Tests: `src/update/recovery.test.ts`, `src/update/rollback.test.ts`.

### Production Trust Configuration

Production updates are disabled when any required approved value is absent. The `FixedOriginTransport` rejects requests when the metadata or artifact origin is missing, and `assertPolicyBinding` rejects a policy whose platform/architecture does not match the running launcher.

Implementation: `src/update/network.ts:FixedOriginTransport`, `src/update/policy.ts:assertPolicyBinding`.

Test-only keys and certificates are labeled `TEST_ONLY` and cannot be used as production trust roots. The fixture certificate at `test/v0.4.0-update/fixtures/localhost-cert.pem` is trusted only through an explicit `https.Agent` in tests.

### Native Fixture Engine

A minimal C fixture engine (`test/v0.4.0-update/fixtures/fixture-engine.c`) is compiled on demand by `src/update/health.native.test.ts` when a host C compiler is available. It prints a fixed version string in response to `--version` and is used to prove that the launcher's health check accepts a real native binary. The fixture is never shipped in the npm package.

## Invariants

- Network transport does not decide whether content is trusted.
- Authentication completes before archive extraction.
- No untrusted manifest value becomes a shell command.
- No remote bytes execute before all authentication and compatibility checks.
- Downloaded artifacts remain non-executable before verification.
- The verified file descriptor, not an attacker-replaceable pathname, feeds extraction.
- Hostile paths and archive entries are rejected, not sanitized.
- Duplicate normalized archive paths are rejected.
- File-count, decompressed-size, and compression-ratio limits are enforced.
- Pre-activation failure preserves the current installation.
- Recovery produces a complete old or complete new installation, never a mixture.
- A locked Windows executable does not corrupt activation.
- Rollback material is independently re-verified.
- Automatic rollback never lowers anti-downgrade floors.
- Production release credentials never enter source, tests, logs, packages, or ordinary CI.
